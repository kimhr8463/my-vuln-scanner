# MongoDB NoSQL Injection Rule trial

`rules/javascript/nosql_injection.yml` contains two intentionally distinct Semgrep Rule IDs. Both map to CWE-943, which covers unneutralized special elements that change data-query logic, including NoSQL queries. CWE-89 remains reserved for SQL; neither existing SQL nor Python Rules were modified.

| Rule | Source / condition | Sink / report meaning |
| --- | --- | --- |
| `javascript-mongodb-nosql-injection-taint` | Express `req.query`, `req.body`, `req.params` fields or raw request object | Tainted `$where` expression or tainted query object passed to `db.collection(...).find/findOne/update`, including a local collection alias. HIGH confidence within a file; `parseInt`, `Number.parseInt`, and `Number` conversion are sanitizers for query-logic injection. |
| `javascript-mongodb-dynamic-where-candidate` | A function parameter is interpolated into a `$where` template literal | MEDIUM-confidence structural candidate. It does **not** establish HTTP taint or MongoDB execution; a reviewer must inspect the caller, value validation, and use of the returned query. |

The structural Rule is deliberately narrower than all dynamic `$where` values: it looks for interpolation of a function parameter. It therefore identifies the pinned NodeGoat DAO path without duplicating the same-file request-taint fixture. It can still flag safe numeric parameters or dead code, and can miss renamed/derived parameters, concatenation, function expressions not covered by its two shapes, or computed keys. The taint Rule can miss other request frameworks, collection aliases beyond local `const ... = db.collection(...)`, some MongoDB APIs, and all route-to-DAO taint in Semgrep Community Edition. Raw request objects sent to a MongoDB query API are treated as candidate operator injection; application-level schema validation must be reviewed to confirm exploitability. An ordinary object's `query()` is **not** a sink in the new Rule.

Use `semgrep test --config rules/javascript/nosql_injection.yml rules/javascript/nosql_injection.js` for annotated Rule tests. Additional separated fixtures under `tests/javascript/nosql/{vulnerable,safe,cross_file}` are exercised by `tests/scanner/test_nosql_rule.py`. They cover direct `$where`, an intermediate variable, direct and local-aliased MongoDB query APIs, fixed `$where`, numeric conversion before a structured query, unrelated `query()`, and a route-to-DAO split. The cross-file fixture produces one structural candidate and **no** taint finding.

At the pinned NodeGoat commit, `GET /allocations/:userId` reads `req.query.threshold` in `app/routes/allocations.js:21` and passes it to `getByUserIdAndThreshold`. The DAO interpolates that parameter at `app/data/allocations-dao.js:77-79` before `allocationsCol.find(searchCriteria())`. With all nine Rules, the CLI reports one MEDIUM candidate, saves Markdown and JSON, and returns 2. The new Rule's match alone is not proof of the cross-file source-to-sink path; the earlier independent review supplies that evidence. The original zero-finding review remains bound to its old Rule digest and is unchanged. This new-Rule trial is recorded separately in `validation/rule_trials/nodegoat_nosql.json`.

At the time of this NoSQL trial, the then-current JavaScript SQL Rule treated `ordinaryObject.query(req.body.filter)` as SQL Injection. A subsequent SQL Rule precision change added SQL-text context and receiver restrictions; the same safe fixture now produces zero findings with all JavaScript Rules. The historical trial record and pinned independent review remain unchanged.
